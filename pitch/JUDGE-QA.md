**Q1. Be honest — isn't this just Prometheus + Grafana + an LLM wrapper? Coroot already does eBPF service maps and Robusta already does AI root-cause on Kubernetes. What does Vigil do that I can't assemble in a weekend?**

The assembled stack does the opposite of Vigil's core claim. Robusta/AIOps tools put an LLM IN the decision path — they generate the root cause, so they can fabricate one. Vigil has 0 LLM calls in the detection/scrape/match hot path, enforced by a CI import-firewall: 9 deterministic packages are mechanically forbidden from even importing the model layer (firewall_test.go fails the build on breach, and there are 8 separate firewall tests — candidate, dgx, assoc, trace, audit, notify, logtmpl, rightsizing). What you assemble in a weekend can hallucinate a cause and has no way to prove it didn't. Vigil's product is the proof: it never invents a causal direction (0 invented arrows — only a named human authors a 'cause' edge; everything else is a labelled ASSOCIATION), and its claim-referee caught 16/16 fabricated causes while wrongly blocking 0/17 true ones. That referee is the thing the weekend stack structurally cannot have.

> 🎤 *Everyone else bolts an LLM onto the answer. We bolt a firewall in front of it — and a referee behind it.*  
> `grounding:` 8 import-firewall tests in obsd/internal/*/firewall_test.go; SUCCESS-METRICS §4 ($0 hot-path inference, firewall_test.go); §2 validate-claim 16/16 caught, 0/17 false-blocks; §6 'invented causal directions: 0'.

### Anti-hallucination architecture & cost ("isn't this just a GPT wrapper over metrics?")

**Q1. Be honest — strip away the marketing and isn't this just an LLM reading metrics and guessing causes? What is actually deterministic versus model output?**

No LLM touches detection. The entire monitoring path — scrape, anomaly detection, forecasting, cross-service joins, graph eval — is deterministic Go that runs 15s scrape + 15s evaluate forever with zero model calls, and a CI import-firewall (obsd/internal/candidate/firewall_test.go and dgx/firewall_test.go) mechanically forbids the 9 replay-deterministic packages from even importing the candidate store or the LLM-agent package. The LLM (DeepSeek) is invoked only when a human clicks 'Ask' or runs governance triage; it reads classed facts via read-only MCP tools and produces a labelled ADVISORY, never a detection. So 'just an LLM over metrics' is exactly the architecture we firewalled against, and a single import would flip the gate red.

> 🎤 *The LLM can't even be imported by the detection engine — that's not a promise, it's a failing build.*  
> `grounding:` firewall_test.go: go list -deps over 9 pkgs {detect,selection,binding,observe,forecast,qss,graph,clock,replay} fails if internal/candidate or internal/dgx is transitively reachable. Detection cadence 15s/15s, $0 inference (SUCCESS-METRICS §4).

**Q2. Fine — but the moment the LLM speaks, it can hallucinate a root cause. What stops it from confidently telling my on-call a fabricated cause and getting believed?**

Three layers. First, provenance labelling: every claim carries a class — MEASURED / PROJECTED / AUTHORED / ASSOCIATION / ADVISORY — and the LLM's output is always ADVISORY, never AUTHORED; an arrow only becomes a 'cause' when a named human authors the relation (0 invented causal directions, with the words 'cause/root cause' test-asserted to appear nowhere in the system scaffolding). Second, a claim-referee gate catches fabrications: 16/16 invented causes caught, 0/17 legitimate claims wrongly blocked. Third, the agent is grounded — it can only cite facts returned by the read-only MCP tools, so a hallucinated cause has no MEASURED evidence behind it and surfaces as unsupported.

> 🎤 *The AI can suggest, but only a human's signature turns a suggestion into a 'cause' — and the referee catches 16/16 fabrications.*  
> `grounding:` SUCCESS-METRICS §2 (claim-referee 16/16 caught, 0/17 false-block), §6 (0 invented causal directions; 'cause' appears nowhere — root-cause-chain test). 5 provenance classes (§6).

**Q3. Why DeepSeek and not GPT-4o or Claude? That reads like you cheaped out on the model — doesn't a weaker model hallucinate more?**

The model choice is deliberately low-stakes because of the architecture: the LLM is a constrained, grounded summarizer over MCP-returned facts, not the reasoning engine that decides truth — so it's swappable, and the provider call is vendor-agnostic (a thinking-disable escape hatch plus SetMaxTokens/DGX_MAX_TOKENS work across deepseek-reasoner, deepseek-v4-flash, or any OpenAI-compatible endpoint). DeepSeek gives reasoning-grade quality at sub-cent cost (~$0.004–0.015/query), which matters because the value is in the grounding and the referee, not the raw model. Honestly: we haven't run a head-to-head hallucination benchmark across providers — that's estimate-level — but since every answer is fact-gated and referee-checked, a stronger model raises polish, not safety.

> 🎤 *We made the model swappable and cheap precisely because we refused to let it be load-bearing.*  
> `grounding:` provider.go vendor-agnostic (SetMaxTokens/DGX_MAX_TOKENS, thinking-disable escape hatch across deepseek-reasoner/v4-flash). Cost ~$0.004–0.015/query (SUCCESS-METRICS §4). Honest caveat: no cross-provider hallucination benchmark run (estimate).

**Q5. Can this AI take a wrong action — restart a pod, scale a deployment, edit my graph — and break production while 'helping'?**

### Correctness & test methodology (how do I know it's RIGHT — FP/FN rates, reproducibility, are the 1.000s cherry-picked)

> 🎤 *The floor is 0.90 and we score 1.000 — if we were fudging, we'd have moved the floor, not beaten it.*  
> `grounding:` crossservice_gate.py:46-49 (ROOT_ACCURACY_MIN=1.0, FALSE_CASCADE_MAX=0, MIN_FIRED_TICKS=5, MIN_DISTINCT_ROOTS=2); validate_claim_gate.py:40 (RECALL_FLOOR=0.90) vs measured 16/16; corpus/validate-claim/verdicts.jsonl = 33 lines (16 expectFlagged:true + 17 false).

### Restraint & Honesty-as-a-feature (why refusing to guess the root cause is the product, not a cop-out)

**Q1. Cut the philosophy. If your tool refuses to tell me the root cause and a competitor just gives me one, the competitor is more useful and yours is a cop-out. Defend that.**

Vigil doesn't refuse to help — it refuses to FABRICATE the one thing it can't measure: causal direction. It still hands you the full picture: the measured fault on each node, every co-onset association, the observed-flow edges, and the named upstream that's actually degraded. The only thing it won't do is print 'X caused Y' when it has no authored arrow proving X→Y. We can measure how often a confident guesser would be lying to you: our AI referee caught 16/16 fabricated causes thrown at it, and our own root-cause surface is test-asserted to contain ZERO cause-words in its scaffolding. A guesser that's wrong sends you to restart the wrong service at 3am — that's negative utility, not neutral.

> 🎤 *A wrong root cause isn't 'more useful,' it's a confident lie that costs you a 3am misfire — we'd rather hand you the evidence and the real arrow.*  
> `grounding:` validate-claim-gate: 16/16 fabrications caught, 0/17 true claims blocked; rootcause_test.go:74 asserts forbidden cause-words ('cause','because of','due to') appear NOWHERE in the root-cause surface; rootcause.go:14 'A JOIN, never a fusion — and never a X caused Y'

**Q2. Okay, but a 'labelled association' is a weasel-word for 'I don't actually know.' Why is that better than a confident answer?**

Because the association is TRUE and the confident answer is a coin-flip. An ASSOCIATION says 'these two failures started together and there's an observed-flow edge between them' — that's a measured fact you can act on. A confident causal answer from a correlation engine invents direction it never observed; correlation has no arrow. The honest move is to surface the real association AND the named upstream that's visibly degraded — on our live runs the cross-service lane names the visible degraded node with 1.000 root accuracy and 0 false cascades. You lose a fabricated sentence; you keep a provable fact plus a correct pointer. The operator's brain supplies the arrow far better than a hallucination does.

> 🎤 *Correlation has no arrow — so we hand you the correlation honestly labelled, not a coin-flip dressed up as a conclusion.*  
> `grounding:` xsvc-gate: 1.000 root + 1.000 caller recall + 1.000 caller precision, 0 false cascades over 20 fired ticks/2 topologies; 5 provenance classes incl. ASSOCIATION badge; obsd/internal/assoc lane (256-deep) is lag-0 co-onset, charter-bound not to claim direction

**Q3. Then how does an operator actually GET to the cause? You've told me what you won't say — walk me through getting an answer.**

Three layers, escalating. (1) Vigil deterministically hands you the measured faults, the co-onset associations, the dependency edges, and the named degraded upstream — for most incidents the visible-degraded-node answer IS operationally the cause. (2) For the 'why' arrow, a NAMED human authors a relation once (e.g. 'memory pressure → OOM → restart'); from then on that arrow is reused forever and surfaced verbatim — it's AUTHORED provenance, written once, replayed deterministically. (3) The 'Ask' agent (DeepSeek, read-only) calls 16-23 MCP tools to ground a WHAT/WHEN/WHY/HOW advisory from those classed facts at sub-cent cost. So the human authors the arrow once; the machine measures everything else and never invents the arrow in between.

> 🎤 *The human authors the arrow once and it's reused forever; the engine measures everything else and the agent narrates it — nobody guesses.*  
> `grounding:` rootcause.go:46 'oriented only by the authored relation'; detect/cascade.go:35 Why field = 'the AUTHORED relation note, verbatim'; governance refuses any decision without authorizedBy (named human); Ask agent = 16-23 MCP calls/query at ~$0.004-0.015

**Q4. This 'restraint' sounds like a marketing story you tell. What actually STOPS the system from guessing — or is it just a convention your code politely follows?**

It's mechanically enforced, not a convention. Detection has ZERO LLM calls — a CI import-firewall test proves the deterministic packages literally cannot even IMPORT the model layer (8 firewall_test.go files across candidate/notify/trace/dgx/audit/assoc/logtmpl/rightsizing). The agent has 0 write-tools to the graph; it physically cannot author a cause. The root-cause surface is test-asserted to contain 0 cause-words. ### Forecasting / early-warning credibility (predicting OOM crossings)

**Q1. Come on — you can't 'predict' an OOM. A pod's memory is driven by request traffic and GC. Isn't this just a glorified threshold alert with a linear ruler drawn through the last few points?**

It is genuinely not a threshold rule. A threshold fires when memory IS high; Vigil stays SILENT while memory is below the bar and only emits a card when a FORECAST trajectory is projected to cross that bar inside the 1h horizon — in project.go if crossIndex() finds no crossing within the horizon the target returns SilenceNoCrossing and you hear nothing. And it isn't a straight ruler: clockd runs a TimesFM 2.5 foundation model that produces a full quantile fan, and before inference we decompose the series — splice the context at the most recent regime shift and subtract event footprints — which cut hidden crossings from 95 to 16 (-83%). A linear extrapolation can't reduce error by 83% because it has no notion of regime. The bar itself is borrowed (a real OOM limit / authored SLO), never invented by us.

> 🎤 *A threshold yells when you're already on fire; Vigil stays quiet until the smoke is on a trajectory through the ceiling.*  
> `grounding:` project.go:90,103-110 (SilenceNoCrossing if no crossing in horizon); decompose.go:14 (regime splice + footprint subtraction); decomposition-09M5.md:156 — hidden crossings 95→16 (−83%); clockd TimesFM 2.5 (google/timesfm-2.5-200m-pytorch).

**Q2. Give me the real accuracy number — not a marketing one. What is recall, what is calibration, and over what corpus? And don't quote me 0.98 coverage, because I won't believe it.**

Recall on genuine OOM crossings is 1.00 (3/3 in the decomposition gate, each warned >=2 min ahead; the plateau and robustness re-gates hold recall 1.00 over 213,978 points and 93/93 in-band). Calibration — the honest one — is band coverage 0.806 against a nominal 0.8 target. We deliberately did NOT pin it to 0.98: a 98% band would be so wide it's useless, and a band that's always right is a band that's too big to act on. 0.806 means the truth lands inside our stated uncertainty band ~81% of the time when we aimed for 80% — that's CALIBRATED, not overconfident. The honest caveat: these are exact floors over curated single-leaker corpora, so '0 false alarms' is 'not-yet-contradicted,' not a production false-positive rate — a near-miss corpus is explicitly on the backlog.

> 🎤 *We could have shown you 0.98 coverage and been useless; we show you 0.806 because a calibrated band you can act on beats a wide band that's always 'right.'*  
> `grounding:` decomposition-09M5.md:147 (recall 1.00, 3/3, >=2min); :153 (band 0.806 vs 0.8 nominal); forecast gate 09M3 (band 0.755 over 213,978 pts, 0/16 false); robustness audit (band 0.804, 93/93 in-band); SUCCESS-METRICS.md §9 caveat — single-leaker corpus, '0 false' = not-yet-contradicted.

**Q3. Why TimesFM and not just an EWMA or Holt-Winters? Sounds like resume-driven over-engineering for a memory line that only goes up.**

Two reasons, both load-bearing. First, the band: TimesFM emits a native quantile fan, which is what makes the uncertainty band a measured output rather than a hand-tuned multiplier — and the band is mandatory and content-checked never to collapse to a line (calibrate.go guarantees a nonzero spread stays nonzero). Second, regime handling: real workloads aren't monotonic ramps — they have rollouts, traffic regimes, plateaus. A foundation model plus our decompose/regime-shift pre-pass is what dropped hidden crossings 83% and lets us SILENCE a projection when an undeclared baseline shift left too little new history (SilenceRegimeShift) rather than confidently forecasting off a stale baseline. EWMA gives you neither a calibrated band nor regime awareness. That said — TimesFM is swappable behind the clock.Clock interface; the discipline (band + crossing-gate + silence) is the product, not the specific model.

> 🎤 *We didn't pick TimesFM for the logo — we picked it for the quantile fan that makes the uncertainty band honest and the regime-awareness that keeps us quiet when we shouldn't speak.*  
> `grounding:` runner.go:16 (Clock interface — model is swappable); calibrate.go:13-15 (quantile order preserved, band never collapses); project.go:56 Quantiles + Bands fan; regimeshift.go / SilenceRegimeShift (project.go:94); decompose 95→16.

**Q4. False alarms are how monitoring tools die. If you cry wolf on a memory blip, every operator mutes you in a week. What stops that?**

Three explicit guardrails, all in code. (1) The default output is SILENCE — every non-crossing target emits an auditable Silence with a reason (no-crossing, flat-series, short-context, band-too-wide), so the system is biased to say nothing. (2) A point trajectory must cross within the horizon; a wide 'could be anytime' cone spanning most of the horizon is silenced as band-too-wide — but, importantly, we judge that as a fraction of the horizon, NOT relative to time-to-cross, because the naive ratio inverted urgency and muted tight imminent crossings exactly when they mattered. (3) Early/cold-start projections are FLAGGED low-confidence, not hidden and not fabricated. Honest weakness: our '0 false' number comes from a monotonic corpus that didn't exercise the false-warning branch hard, so I'd call the false-alarm rate 'designed-low and gate-clean,' with a near-miss corpus as the next earned step.

> 🎤 *The default isn't an alert — it's an audited silence; we make you earn a card, not the other way around.*  
> `grounding:` project.go:72-95 (Silence with enumerated reasons; SILENCE is default); project.go:124-132 (band-too-wide judged as fraction of horizon, not time-to-cross); trend.go:45-48 / EarlyOnset flagged not silenced; SUCCESS-METRICS.md §9 (0-false = single-leaker, not-yet-contradicted).

The fragility you saw is a hardcoded SSH tunnel to a single AWS k3s box: when AWS hands out a new public IP after a restart, one file needs an IP edit and obsd needs a restart because it intentionally exits when its data source drops. That last part is actually a feature: obsd fails CLOSED — it would rather die than emit findings against a stale or absent stream, which is the same honesty discipline as the silence ledger. The engine proper is a single 76 MB static Go binary, one process, 15s scrape + 15s evaluate, with byte-identical replay and a content-pinned graph (sha256:f13e5101) that rejects tampering. In a real deployment obsd runs in-cluster against a stable scrape endpoint — no tunnel, no dynamic IP. So the brittleness is the laptop-to-cloud demo rig; the production posture is 'fail closed and stay deterministic.'

> 🎤 *The tunnel is duct tape on the demo; obsd dying when its data dies is not a bug, it's the engine refusing to lie about a stream it can't see.*

**Q5. You call yourselves an observability engine, but you admit you can't read application logs and your app-SLO/DB-metric lane is dormant. Isn't 70-80% of real stateful-app root cause invisible to you? What's left?**

For a stateful app, a large fraction of root-cause signal does live in surfaces we structurally can't read today — and we name every one: APPLICATION_LOGS (no log lane; we read only 3 Kubernetes event reasons), APP_DB_INTERNAL_METRICS (the --app-metrics lane exists but is DORMANT — no exporters, no vigil.io/slo.* annotations), L7_PROTOCOL_SEMANTICS (flow edges are L3/L4 TCP-only — we see a connection exists, not its HTTP status or SQL identity), and MISSING_EVENT_REASONS. So app-SLO phenomena genuinely need instrumentation the operator must deploy — exporters, annotations, an L7 tap — and each blind spot's UnblockedBy field spells out exactly what. What Vigil IS, honestly, is a deterministic infrastructure-symptom detector plus a dependency graph: it covers the container/node/object resource layer well (7 phenomena full-wired on a vanilla kind cluster, more on richer clusters), forecasts resource exhaustion ~10 min ahead, and never fabricates the app-layer cause it can't see. The honest framing is 'symptom detector + topology that admits its app-layer ceiling,' not 'full-stack root-cause oracle.'

> 🎤 *We'd rather be a deterministic infra detector that names its app-layer ceiling than a full-stack 'root-cause AI' that hallucinates the log line it never read.*
